# 三应用联动测试需求 MRD（3 人日）

## 背景

当前需要验证 AI Coding Pipeline 对多应用上传、多应用需求拆解、动态 fanout、分支实施、分支 SPEC、Java 实现、测试代码和归档的完整流程能力。测试输入包含三个应用目录：

- crowd：人群圈选/人群策略相关能力。
- abtest：AB 实验平台与营销中台实验配置相关能力。
- cc：触达/拉新/客群运营链路相关能力。

## 目标

在 3 人日内完成一个轻量级的跨应用联动需求：新增“实验人群触达链路的统一追踪标识”。

系统需要在 crowd、abtest、cc 三个应用中形成一致的 `traceKey` 传递和记录能力，用于后续排查一次营销实验从人群圈选、实验分桶到触达执行的完整链路。

## 范围

### crowd 应用

1. 在人群圈选输出结果中补充 `traceKey` 字段。
2. `traceKey` 生成规则：`bizType + activityId + crowdId + yyyyMMddHHmmss`。
3. 输出给下游时保留原有字段，不能破坏已有文档中描述的人群结果结构。

### abtest 应用

1. 实验配置或实验分桶链路接收上游 `traceKey`。
2. 在实验分桶结果中透传 `traceKey`。
3. 当上游没有传入 `traceKey` 时，记录告警日志，并使用 `UNKNOWN_TRACE` 兜底。

### cc 应用

1. 触达任务接收实验分桶结果中的 `traceKey`。
2. 触达执行日志中输出 `traceKey`、`activityId`、`crowdId`、`experimentId`。
3. 触达失败时，错误日志必须包含 `traceKey`，便于链路排查。

## 非目标

- 不改造数据库表结构。
- 不新增异步 MQ topic。
- 不做前端页面。
- 不做复杂权限、灰度或报表。

## 验收标准

1. 需求拆解能够识别 crowd、abtest、cc 三个应用都受影响。
2. 动态 workflow 在当前 session 中生成三个项目分支，而不是固定线性流程。
3. 每个应用分支都生成实施方案、SPEC、Java 实现建议和测试代码建议。
4. 归档产物中能看到三个应用的分支汇总和跨应用审查结果。
5. 若某个应用缺少可直接修改的 Java 源码，流程需要生成明确的变更建议、伪代码或待落地说明，不能静默失败。

## 工期

总工期：3 人日。

- 第 1 人日：需求拆解、三应用影响面分析、接口字段约定。
- 第 2 人日：三应用分支实现建议和测试用例生成。
- 第 3 人日：跨应用链路审查、失败兜底检查、归档。
